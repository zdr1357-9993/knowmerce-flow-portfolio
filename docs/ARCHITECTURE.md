# 구현 구조와 검증 범위

## 해결하는 업무

부서마다 다른 상품·요청 정보를 하나의 품번과 처리 상태로 연결합니다.
요청 작성 → 물류 검토·승인 → 일정 공유 → 입출고 완료·재고 반영을 추적하고,
앨범·MD 주문서 가공과 업체별 예상 비용 비교를 같은 작업 흐름에 둡니다.

## 코드 읽는 순서

1. `lib/model.ts`: 업무 모델, 예시 데이터, 재고·상태 조회 규칙
2. `lib/request-validation.ts`: 상품·날짜·수량·입출고 요청의 공통 입력 검증
3. `lib/actions.ts`: 역할별 허용 동작, 승인·수정·완료·재고 변경과 감사 이력
4. `lib/automation.ts`, `lib/order-files.ts`, `lib/xlsx.ts`: 주문 분할·수량 대조·운임 계산·파일 출력
5. `app/api/workspace/route.ts`: 세션 확인과 명령 처리 순서
6. `lib/workspace-http.ts`: 요청 형식·Origin·바이트 제한과 오류 응답
7. `lib/workspace-store.ts`: D1 읽기·계정 프로필 반영·revision 기반 저장
8. `app/workspace.tsx`, `components/workspace/primitives.tsx`: 화면 조합과 공통 표시·모달

```text
공개 체험 화면 → public-demo → actions / validation → 브라우저별 저장

인증 화면 → API → 세션 확인 → D1 읽기
                           → 입력 검증 / actions / 계정 관리
                           → revision 조건부 저장 → 역할별 응답 필터
```

## 중요한 선택

- 업무 데이터는 `flow_workspaces`의 JSON 문서로 저장합니다. 논리 ERD 전체를 정규화한 ERP DB는 아닙니다.
- 브라우저 공개 체험은 실제 계정 발급·인증 데이터와 분리합니다.
- 전체 워크스페이스 revision이 다른 요청은 409로 거부합니다. 개별 요청의 version 검사도 유지합니다.
- 계정 변경과 워크스페이스 저장은 같은 D1 batch 안에서 처리하고, 계정 SQL에도 revision 조건을 둡니다.
- 재고 미확인(null)과 확인된 0을 구분합니다. 완료 시 모든 품목을 검증한 뒤 재고 이동을 기록합니다.
- 자동화 결과는 입력·계산 기준과 함께 보관하고 재가공 시 새 개정으로 남깁니다.

## 자동 검사

`pnpm test`는 기존 업무·권한 검사, 공개 체험 격리, HTTP 명령 계약·보안 경계,
비밀번호 해시·세션 쿠키 검사를 실행합니다. 외부 서비스나 비밀값이 필요하지 않습니다.

`tests/accounts-integration.mjs`는 별도 로컬 서버와 테스트 계정이 필요합니다.
계정 생성·비밀번호 변경·세션 무효화를 실제 API에서 확인하며 운영 서버 실행을 차단합니다.
이 검사를 실행하지 않은 상태를 인증 E2E 검증 완료로 표현하지 않습니다.

## 남은 범위

- 실제 Slack 전송, WMS 제출, 실시간 ML 추론은 연결하지 않았습니다.
- 원본 업로드는 CSV이며 출력은 XLSX입니다. XLSX 입력 전체 지원은 아닙니다.
- 자동 검사가 브라우저·D1·사용자 전체 경로를 모두 대체하지 않습니다.
- `app/workspace.tsx`의 기능별 화면 분리는 후속 작업입니다. 이번 변경은 공통 UI·입력 검증·저장 경계 분리와 읽기 쉬운 형식에 집중했습니다.
